# התפקיד שאיתו מתחברים ל-Neon

> אם ראיתם את ההודעה **«ההפרדה בין בתים לא פעילה במסד הנתונים הזה»** —
> הדף הזה הוא התיקון, וזה לוקח שלוש דקות.

---

## מה קרה

אבטחת שורות (RLS) היא מה שמפריד בין בתים בקאסה. Postgres **מתעלם ממנה לחלוטין**
עבור תפקיד שהוא `superuser` או שיש לו `BYPASSRLS` — כל מדיניות עדיין רשומה, כל
טבלה עדיין מדווחת `rowsecurity = true`, ושום דבר בשום מקום לא מתלונן. הסימפטום
היחיד הוא בית אחד שקורא את הכסף של בית אחר.

**תפקיד ברירת המחדל של Neon, `neondb_owner`, נוצר עם `BYPASSRLS`.**

לכן:

- **הרצת המיגרציה שוב לא תעזור, ולעולם לא תעזור.** המיגרציה יוצרת את המדיניות
  נכון בכל פעם. הבעיה היא בתפקיד שמתחבר, לא בסכימה.
- התפקיד גם לא יכול להסיר את התכונה מעצמו. נבדק:
  `ALTER ROLE neondb_owner NOBYPASSRLS` → `ERROR: permission denied to alter role`.

התיקון הוא תפקיד אפליקציה ייעודי, בלי `BYPASSRLS`.

---

## התיקון

### 1. בחרו סיסמה — אותיות וספרות בלבד

```bash
openssl rand -hex 24
```

**`-hex`, לא `-base64`.** base64 מייצר גם `/`, `+` ו-`=`, ו-`/` בתוך סיסמה
במחרוזת חיבור **שוברת את הכתובת**: כל מה שאחריו נקרא כשם מסד הנתונים. אם אתם
מייצרים סיסמה בכלי אחר — ודאו שאין בה `@ / : # ? % &`.

שמרו אותה. Neon לא תוכל להראות לכם אותה שוב: היא נקבעת ב-SQL, לא בקונסולה.

### 2. הריצו את זה ב-Neon → SQL Editor

**בתור `neondb_owner`**, על מסד הנתונים של קאסה. החליפו את `הסיסמה-שלכם`:

```sql
CREATE ROLE casa_app LOGIN PASSWORD 'הסיסמה-שלכם'
  NOSUPERUSER NOBYPASSRLS NOCREATEDB NOCREATEROLE;

-- כדי שנוכל להעביר לו בעלות בשלב הבא
GRANT casa_app TO neondb_owner;

-- הבעלות על הטבלאות עוברת אליו: בלעדיה המיגרציה הבאה תיכשל,
-- כי ALTER TABLE דורש בעלות. הנתונים עצמם לא זזים ולא משתנים.
REASSIGN OWNED BY neondb_owner TO casa_app;

GRANT USAGE, CREATE ON SCHEMA public TO casa_app;
```

> ### ⚠ תפקיד שייך לענף אחד, לא לפרויקט
>
> ענף ב-Neon הוא עותק מלא — כולל רשימת התפקידים. תפקיד שנוצר על `main` אינו
> קיים על ענף גיבוי שנוצר לפניו, ותפקיד שנוצר על ענף גיבוי אינו קיים על `main`.
> לכל ענף יש מארח `ep-…` משלו, ולכן **המארח שב-`DATABASE_URL` הוא שקובע על איזה
> ענף החיבור נוחת.**
>
> זה מסוכן במיוחד מפני ש-Postgres מחזיר `28P01` — «אימות סיסמה נכשל» — גם
> כשהתפקיד פשוט **לא קיים**. סיסמה נכונה לחלוטין, על הענף הלא נכון, נראית בדיוק
> כמו שגיאת הקלדה.
>
> בראש ה-SQL Editor יש בורר ענף. לפני שמריצים את שלב 2 — ודאו שהוא מצביע על
> אותו ענף שאליו `DATABASE_URL` מתחבר, בדרך כלל `main`.

### 3. אמתו — לפני שנוגעים ב-Vercel

עדיין ב-SQL Editor, **על אותו ענף**:

```sql
SELECT current_database(), rolname, rolsuper, rolbypassrls, rolcanlogin
  FROM pg_roles WHERE rolname = 'casa_app';
```

חייב להחזיר שורה אחת: `casa`, `casa_app`, `f`, `f`, `t`. אם לא — עצרו כאן.

**שורה ריקה פירושה שהתפקיד אינו קיים על הענף הזה.** אם שלב 2 הצליח קודם, החליפו
ענף בבורר והריצו שוב את השאילתה עד שתמצאו על איזה ענף הוא כן יושב — זו התשובה
לשאלה למה `DATABASE_URL` נדחה.

### 4. עדכנו את `DATABASE_URL` ב-Vercel

**זה השלב שבו התיקון נכנס לתוקף.** שלב 2 יצר תפקיד בטוח; `DATABASE_URL` הוא
הדבר היחיד שקובע באיזה תפקיד האפליקציה מתחברת. בלי השלב הזה היא תמשיך להתחבר
בתור `neondb_owner`, וההודעה תישאר זהה.

**איפה:** Vercel → הפרויקט `casa` → **Settings** → **Environment Variables** →
השורה `DATABASE_URL` → שלוש הנקודות ← **Edit**.

**גבו לפני:** העתיקו את הערך הקיים לאיזשהו מקום. זו דרך החזרה היחידה אם משהו
משתבש.

**מבנה המחרוזת:**

```
postgresql://neondb_owner:npg_QwErTy@ep-cool-dawn-12345-pooler.eu-central-1.aws.neon.tech/casa?sslmode=require
             └─ משתמש ──┘ └─ סיסמה ─┘ └────────────────── מארח ──────────────────────────┘ └מסד┘ └─ פרמטרים ─┘
```

**משנים רק את מה שבין `//` לבין `@`.** כל מה שמ-`@` והלאה נשאר תו-בתו:

```
postgresql://casa_app:הסיסמה-משלב-1@ep-cool-dawn-12345-pooler.eu-central-1.aws.neon.tech/casa?sslmode=require
```

שלוש טעויות נפוצות:

- **המארח חייב להישאר עם `-pooler`.** בלעדיו כל פונקציה פותחת חיבור ישיר, ומכסת
  החיבורים של Neon נגמרת תחת עומס.
- **`?sslmode=require` נשאר.** הקוד מרפה אבטחת TLS רק מול `sslmode=disable`
  מפורש, ובלי הפרמטר אתם מסתמכים על ברירת מחדל.
- **הסביבה:** ודאו שהעריכה חלה על **Production**. אם הערך מוגדר גם ל-Preview
  ו-Development, עדכנו אותם גם, אחרת פריסות Preview ימשיכו לדלוף.

### 5. רידפלוי — חובה

**שינוי משתנה סביבה לא משפיע על פריסה קיימת.** הפונקציות קוראות את הערך כשהן
עולות, אז צריך פריסה חדשה:

Vercel → **Deployments** → הפריסה העליונה → שלוש הנקודות ← **Redeploy**.

### 6. בדקו

«הגדרות» ← «מסד הנתונים» ← **«הפרדה בין בתים»** צריך לומר **«נאכפת»**.

אם עדיין כתוב «לא פעילה», אחד משלושת אלה קרה: הרידפלוי לא הסתיים, `DATABASE_URL`
נערך בסביבה הלא נכונה, או שהסיסמה מכילה תו שבור והחיבור נופל אחורה. בדקו את
הלוג ב-Vercel → Deployments → Runtime Logs.

## לראות מה `DATABASE_URL` באמת מכיל

`DATABASE_URL` מוגדר ב-Vercel כ-**Secret**, כלומר לכתיבה בלבד: אחרי השמירה אי
אפשר להציג אותו שוב, גם לא לבעלים. זו ההגדרה הנכונה לסיסמה — ובדיוק היא שהופכת
`28P01` לבלתי אפשרי לפתירה בעין, כי השאלה היחידה שחשובה («כאיזה משתמש, לאיזה
מארח, לאיזה מסד ניסינו?») אין לה תשובה בשום מסך.

לכן **התהליך שכן מחזיק את המחרוזת מדווח מה הוא מחזיק.** כל כשל חיבור
(`28P01`, `42501`, `3D000`, `ENOTFOUND`, פסקי זמן) שולח לטלגרם שורה כזו:

```
DATABASE_URL שהפונקציה קיבלה — בלי הסיסמה:
casa_app@ep-beige-globe-12345-pooler.eu-central-1.aws.neon.tech/casa?sslmode=require
סיסמה: 48 תווים
```

הסיסמה עצמה לעולם לא נשלחת — רק אורכה, ואם יש בה תו שישבור את הכתובת (`/`, `?`,
`#`, רווח) גם התו הזה נקרא בשמו. ההודעה נשלחת לצ׳אט אחד פרטי, ומכילה רק את
ההגדרה שלנו — תפקיד, מארח, שם מסד — אף פעם לא נתונים של בית.

מה לעשות עם השורה הזו:

| מה שרואים | מה זה אומר |
|---|---|
| `neondb_owner@…` | שלב 4 לא נשמר, או שהרידפלוי לא רץ |
| מסד `neondb` ולא `casa` | נבחר המסד הלא נכון בבורר של Neon |
| `ep-` אחר ממה שרואים ב-Neon | הכתובת מצביעה על ענף אחר — שם התפקיד לא קיים |
| `⚠ המארח בלי -pooler` | הוסר ה-`-pooler` בהעתקה |
| `⚠ תו שובר בסיסמה` | הסיסמה נחתכת לפני שהיא מגיעה למסד — קבעו חדשה ב-hex |
| `⚠ נגרר בהעתקה: גרשיים` | הודבק `psql '…'` במקום המחרוזת עצמה |
| הכול נכון, ועדיין `28P01` | הסיסמה באמת שגויה — `ALTER ROLE` למטה |

### שכחתם את הסיסמה?

**היא לא ניתנת לשחזור, ואין צורך.** Postgres שומר גיבוב SCRAM חד־כיווני, לא את
הסיסמה עצמה — לא ב-`pg_authid`, לא בקונסולה של Neon, בשום מקום. פשוט קובעים
חדשה, ב-SQL Editor בתור `neondb_owner`:

```sql
ALTER ROLE casa_app PASSWORD 'הסיסמה-החדשה';
```

זה כל מה שצריך: התפקיד, הבעלות וההרשאות נשארים כפי שהם, ושום נתון לא זז.

ואם אתם לא בטוחים שהתפקיד בכלל נוצר:

```sql
SELECT rolname, rolsuper, rolbypassrls, rolcanlogin
  FROM pg_roles WHERE rolname = 'casa_app';
```

שורה ריקה = שלב 2 לא רץ, הריצו אותו. שורה עם `f, f, t` = הכול תקין וחסרה רק
הסיסמה.

### חזרה אחורה

אם משהו נשבר: החזירו את `DATABASE_URL` הישן, רידפלוי. `casa_app` נשאר קיים
ולא מזיק, והנתונים לא זזו — `REASSIGN OWNED` שינה בעלות בלבד.

## מה נבדק, ואיך

הרצף כולו הורץ מול Postgres 16 מקומי שמשחזר את המצב של Neon — תפקיד בעלים
שאינו superuser אך יש לו `BYPASSRLS`:

| | לפני | אחרי |
|---|---|---|
| `row_security_active('accounts')` | `false` | `true` |
| בית 1 רואה את החשבון של בית 2 | **כן** | לא |
| חיבור בלי בית רואה | הכול | 0 שורות |
| כתיבה לבית אחר | מצליחה | `ERROR: new row violates row-level security policy` |
| המיגרציה רצה שוב | ✔ | ✔ |
| הנתונים אחרי `REASSIGN` | — | ללא שינוי |

`REASSIGN OWNED` מעביר בעלות בלבד. הוא אינו מעתיק, אינו מוחק ואינו נוגע בשורות.

---

## למה זה לא נתפס קודם

הבדיקה הראשונה של הבידוד רצה בתור superuser ו**עברה את כל המבחנים** — מפני
שהיא ראתה הכול. זה מה שהוליד את `proveIsolation` ב-`api/_lib/db.ts`: המערכת
מסרבת לשרת מסד שבו ההפרדה אינה פועלת, במקום להגיש בשקט את הנתונים של כולם.

הבדיקות ב-`scripts/tests/isolation.test.ts` אומתו משני הכיוונים — כולן עוברות
מול תפקיד רגיל, ושש מהן נכשלות מול תפקיד שעוקף RLS. לכן `CASA_TEST_DATABASE_URL`
חייב להצביע על תפקיד רגיל: אחרת הבדיקות יעברו מהסיבה הלא נכונה.
